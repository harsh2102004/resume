Module 01 • Executive Overview

Project Fundamentals & The Interview Pitch

Master the problem statement, technical rationale, engineering challenges, and how to defend PulseCast across 2-minute and 5-minute interview rounds.

🎯 2-Minute High-Impact Elevator Pitch

"PulseCast is a distributed media streaming platform and synchronized watch party engine built to replicate the core video delivery pipeline of services like YouTube and Netflix. It solves three fundamental challenges in digital video: fault-tolerant resumable file ingestion over flaky networks using the open-standard TUS protocol; low-latency adaptive media delivery via HTTP 206 chunked range streaming and automated FFmpeg HLS transcoding; and real-time multi-peer playback synchronization via WebSockets with client-side clock drift compensation. I built it from the ground up using Node.js, Express, MongoDB Atlas, Cloudinary CDN, and React 19."

Key Interview Takeaway: Never pitch it as "just a video website with CRUD". Pitch it as a media pipeline that handles ingestion, cloud storage, transcoding, chunked streaming, and real-time state synchronization.
⚡ 5-Minute Technical Deep Dive (System Lifecycle)

When an interviewer asks: "Walk me through the architecture and engineering lifecycle of a video in your system." — Deliver this exact 5-step lifecycle:

  1. Ingestion (TUS Protocol): A client selects a 1GB 4K video. Instead of a monolithic multipart POST request that fails on timeout, our client uploads deterministic 2MB binary slices using TUS PATCH requests. If Wi-Fi cuts out at 85%, the client queries the server's current byte offset via HEAD and resumes at byte 850,000,001 without wasted upload bandwidth.
  2. Persistent Cloud Delivery (Cloudinary CDN): Upon upload completion (EVENTS.POST_FINISH), the backend initiates a chunked 6MB upload pipeline to Cloudinary (uploadVideoOnCloudinary). This decouples media storage from ephemeral container filesystems (like Render/Docker) and establishes permanent worldwide CDN edge caching.
  3. Asynchronous FFmpeg Processing: The server triggers decoupled workers. The Transcode Worker encodes video into Apple HLS bundles (360p, 720p with master.m3u8 manifest and .ts segments). The Storyboard Worker extracts frames every 5 seconds into 5x5 image sprites with WebVTT coordinates for cursor hover scrubbing preview.
  4. Dual Streaming Paths: The client player (Hls.js) consumes adaptive HLS for variable networks, while standard playback uses native HTTP 206 Partial Content range requests with 1MB chunk slicing for instantaneous seeking.
  5. Synchronized Watch Party (Socket.io): Viewers join watch rooms. A dynamic host broadcasts playback actions (PLAY, PAUSE, SEEK). Non-host peers run a client-side drift compensation algorithm adjusting playbackRate by ±5% to stay aligned within a 150ms deadband.
📝 Resume Bullet Points
  • Architected full-stack distributed video platform supporting TUS resumable chunked ingestion, reducing upload re-transmission costs by 100% on network drops.
  • Engineered HTTP 206 Byte-Range streaming engine in Node.js, parsing partial range headers to deliver 1MB chunks and sub-second seek latency.
  • Integrated asynchronous FFmpeg transcoding pipeline generating Apple HLS multi-bitrate streams (360p/720p) and 5x5 WebVTT storyboard scrubbing sprites.
  • Constructed WebSocket Watch Party subsystem with dynamic host re-election and client-side clock drift compensation maintaining sub-150ms peer synchronization.
  • Automated CI/CD workflows using GitHub Actions running native Node.js test runners across Node v18-v22 with 100% test pass rate.
🛡️ Defending Architectural Decisions

Q: Why MongoDB over PostgreSQL?
A: Video metadata (transcoding status, dynamic HLS quality arrays, storyboard VTT cues, nested comment threads) benefits from a flexible document model. Mongoose aggregate pipelines also allow complex multi-stage lookups for channel subscribers and analytics without rigid relational migrations.


Q: Why TUS protocol over standard multipart form-data?
A: Form-data uploads are all-or-nothing. If a 500MB upload drops at 490MB, the entire file must be re-sent. TUS provides an open standard with byte offset headers (Upload-Offset, Upload-Length) allowing deterministic pause/resume.

Responsibilities: Renders responsive dark-mode UI, manages JWT auth state in AuthContext.jsx, coordinates chunked uploads via custom TusUploader.js, executes adaptive HLS streaming via HlsPlayer.jsx, and handles synchronized room events in WatchPartyRoom.jsx.

⚠️ Failure Points
  • Ephemeral Disk: On cloud platforms like Render, local files are deleted on container restart. Solved by integrating Cloudinary CDN fallback.
  • FFmpeg CPU Starvation: Running FFmpeg directly inside Node process threads can starve the event loop. Mitigated by async Promise delegation.
  • Socket.io In-Memory State: Active room state is stored in an in-memory JS Map(). Server reboot wipes active rooms without Redis.
🚀 Scalability Bottlenecks
  • Multi-Server Sockets: Multiple backend instances cannot share watch room state without a Redis Pub/Sub adapter.
  • Transcoding Queue: Concurrent uploads trigger multiple concurrent FFmpeg jobs. Requires a distributed queue like BullMQ.
  • Database Reads: High-traffic video views require Redis caching for view counts and video metadata.

Module 03 • Deep Systems

Video Streaming: HTTP 206 & HLS Engineering

Understand streaming from first principles: Byte-Range headers, seeking mechanics, HTTP status codes (200 vs 206 vs 416), master manifests, and adaptive bitrate switching.

📡 HTTP Range Requests From First Principles

Why not just serve video with a standard HTTP 200 OK? Because an HTTP 200 response forces the browser to buffer the entire 1GB file sequentially before or while playing. If a user seeks to minute 45, the browser must download all 44 preceding minutes!

Status Code Header Required Meaning PulseCast Behavior
HTTP 200 OK Content-Length: [Total] Full entity downloaded Used when client doesn't send Range header
HTTP 206 Partial Content Content-Range: bytes start-end/total Discrete byte slice streamed Delivers 1MB video slice via fs.createReadStream
HTTP 416 Range Not Satisfiable Content-Range: bytes */total Requested range exceeds file bounds Returned when start >= fileSize || start > end
Exact Implementation (src/controllers/stream.controller.js):
const range = req.headers.range; // e.g. "bytes=1048576-"
if (!range) {
    res.writeHead(200, {
        "Content-Length": fileSize,
        "Content-Type": video.mimeType || "video/mp4",
        "Accept-Ranges": "bytes",
    });
    return fs.createReadStream(filePath).pipe(res);
}

const parts = range.replace(/bytes=/, "").split("-");
const start = parseInt(parts[0], 10);
const CHUNK_SIZE = 1 * 1024 * 1024; // 1MB Chunk
const end = parts[1] ? parseInt(parts[1], 10) : Math.min(start + CHUNK_SIZE - 1, fileSize - 1);

if (start >= fileSize || end >= fileSize || start > end) {
    res.status(416).set({ "Content-Range": `bytes */${fileSize}` });
    return res.end();
}

const contentLength = (end - start) + 1;
res.writeHead(206, {
    "Content-Range": `bytes ${start}-${end}/${fileSize}`,
    "Accept-Ranges": "bytes",
    "Content-Length": contentLength,
    "Content-Type": video.mimeType || "video/mp4",
});

fs.createReadStream(filePath, { start, end }).pipe(res);
📺 HLS: HTTP Live Streaming Architecture

HLS breaks video into indexed chunks and delivers a hierarchical manifest:

  • Master Playlist (master.m3u8): Declares available streams, bandwidths, and resolutions.
  • Variant Media Playlists (360p.m3u8, 720p.m3u8): Lists sequential 6-second MPEG-TS segments (.ts).
  • Hls.js Client Engine: Monitors buffer health and download speed. If client bandwidth drops below 1.2 Mbps, Hls.js automatically downswitches from 720p to 360p on the next segment boundary without playback interruption.
⚖️ HLS vs Progressive HTTP 206
Dimension HTTP 206 (Progressive) HLS (Adaptive)
Format Single MP4 file Manifest + segmented .ts
Resolution Fixed at encode time Dynamically adapts (360p/720p)
Transcoding Cost Zero (Direct streaming) High (FFmpeg processing)
CDN Caching Cache-byte ranges Highly cacheable static files
Module 04 • Ingestion Protocol

Resumable Upload Engineering (TUS Protocol)

Why traditional multipart uploads fail, the TUS state machine, offset negotiation, concurrent transfer locks, and the @tus/server Express pipeline.

🔄 The TUS Ingestion State Machine
(1) Client POST /api/v1/videos/resumable-upload [Headers: Upload-Length: 104857600, Upload-Metadata: ...]
    ➔ Server returns HTTP 201 Created [Location: /api/v1/videos/resumable-upload/upload_id_9481]

(2) Client PATCH /api/v1/videos/resumable-upload/upload_id_9481 [Upload-Offset: 0, Body: Chunk 1 (2MB)]
    ➔ Server returns HTTP 204 No Content [Upload-Offset: 2097152]

(3) [NETWORK DROPS AT 85%] ➔ Client Reconnects
    Client HEAD /api/v1/videos/resumable-upload/upload_id_9481
    ➔ Server returns HTTP 200 OK [Upload-Offset: 89128960, Upload-Length: 104857600]

(4) Client resumes with PATCH [Upload-Offset: 89128960, Body: Remaining bytes]
    ➔ Upload finishes ➔ Server fires EVENTS.POST_FINISH ➔ Video record created!
🛡️ Security & Storage Details
  • Authentication Gate: In app.js, the route /api/v1/videos/resumable-upload* intercepts incoming POST requests and verifies JWT presence before handing over to TUS datastore.
  • Zero Buffer Memory: @tus/file-store writes directly to disk in public/uploads/resumable via write streams, preventing Node.js Out-Of-Memory (OOM) crashes on large file payloads.
  • Integrity Verification: TUS enforces deterministic byte offsets; if a client attempts to patch with a mismatched Upload-Offset, the server rejects it with 409 Conflict.
☁️ Cloudinary Handoff Pipeline

In src/services/tus.service.js, when EVENTS.POST_FINISH triggers: 

tusServer.on(EVENTS.POST_FINISH, async (req, res, upload) => {
    const storedFilePath = path.join(resumableUploadDir, upload.id);
    // Asynchronously stream to Cloudinary CDN
    const cloudUpload = await uploadVideoOnCloudinary(storedFilePath);
    if (cloudUpload?.secure_url) {
        video.videoFile = cloudUpload.secure_url;
        video.thumbnail = cloudUpload.secure_url.replace(/\.[^/.]+$/, ".jpg");
    }
    await video.save();
});
Module 05 • Media Processing

FFmpeg & Media Processing Architecture

Codecs vs containers, asynchronous transcode workers, multi-bitrate HLS encoding, 5x5 sprite sheet tiling, and WebVTT cue coordinate generation.

🎬 Codecs vs Containers Fundamentals

Container (e.g., MP4, MKV, WebM): The wrapper file that packages video streams, audio streams, subtitle tracks, and metadata synchronization info together.


Codec (e.g., H.264 / AVC, H.265 / HEVC, VP9, AAC): The compression algorithm that encodes raw pixel matrices into compressed digital bitstreams and decodes them on playback.


Transcoding: Decompressing an input stream with Codec A and re-encoding it into Codec B (e.g., raw camera footage to H.264/AAC for browser compatibility).

🖼️ Storyboard Scrubbing Sprites (5x5 Grid)

In src/workers/storyboard.worker.js, frames are sampled every 5s and tiled into 5x5 grids:

It creates WebVTT cues mapping timeline seconds to spatial coordinates:

00:00:05.000 --> 00:00:10.000
/uploads/storyboards/id/sprite_001.jpg#xywh=160,0,160,90
⚙️ The Asynchronous Worker Thread Model

Why media processing MUST NEVER block the Express event loop:

FFmpeg is extremely CPU-intensive. A single 1080p transcode can consume 100% of 4 CPU cores for several minutes. If executed synchronously inside an Express route handler, Node.js cannot process incoming I/O events, causing all other user requests to time out (HTTP 504). In PulseCast, workers run asynchronously in detached promises after TUS upload completes, logging status directly to MongoDB (transcodingStatus: "PROCESSING" | "COMPLETED" | "FAILED").

Module 06 • Real-Time Systems

Real-Time Watch Party: WebSockets & Clock Sync

Socket.io rooms, host re-election, server-authoritative state, network jitter, and the reality check on the claimed sub-50ms synchronization tolerance.

🔍 Code Reality Check: Sub-50ms Sync Tolerance
Critical Code Audit Finding: While the README claimed "sub-50ms synchronization tolerance", inspecting the actual source code in frontend/src/components/WatchPartyRoom.jsx (lines 67-82) reveals:
  • Deadband: absDrift <= 0.15 (150ms deadband, not 50ms). Minor drifts under 150ms do not trigger adjustments to avoid audible pitch changes.
  • Soft Drift: 0.15 < absDrift <= 1.5 adjusts video.playbackRate = drift < 0 ? 1.05 : 0.95 to converge smoothly.
  • Hard Seek: absDrift > 1.5 forces video.currentTime = serverTime to catch up instantly.
Interview Tip: Explaining that you audited and tuned the deadband to 150ms because a 50ms threshold caused constant micro-stutters and audio warping on consumer Wi-Fi demonstrates real engineering maturity!
👑 Dynamic Host Election Algorithm

In src/sockets/watchParty.socket.js:

  1. First socket to emit join-room is designated isHost = true.
  2. When the host disconnects, the server executes: 
    const nextHost = room.participants.values().next().value;
if (nextHost) {
    nextHost.isHost = true;
    room.hostSocketId = nextHost.socketId;
    io.to(roomId).emit("host-changed", { newHost: nextHost });
}
  3. Host privileges seamlessly transfer to the next connected peer without tearing down the room!
🔄 Sync Action Lifecycle
  1. Host pauses video ➔ emits sync-action: { action: "PAUSE", currentTime: 42.5 }.
  2. Server updates in-memory room state and broadcasts to room peers.
  3. Peers receive event, set isRemoteActionRef.current = true (to prevent feedback loops), and pause video at 42.5s.
  4. A 150ms timeout resets the remote action guard.
Module 07 • Security Engineering

Authentication, Cryptography & Stream Security

JWT access/refresh token rotation, bcrypt salting, constant-time HMAC-SHA256 URL signing with timingSafeEqual, and XSS/CSRF mitigations.

🔑 Dual Token Rotation (JWT)
  • Access Token: Short-lived (1 day), signed with ACCESS_TOKEN_SECRET. Carries user ID, email, and username in payload. Sent in Authorization header or HTTP-only cookie.
  • Refresh Token: Long-lived (10 days), signed with REFRESH_TOKEN_SECRET. Persisted in MongoDB user record.
  • Rotation Flow: When access token expires, client hits POST /api/v1/users/refresh-token. Server validates incoming token against database; if valid, both tokens are re-issued.
  • Audit Note: Current code checks incomingToken !== user.refreshToken. Full automatic family revocation upon reuse is a planned security enhancement.
🛡️ Constant-Time HMAC Stream Protection

In src/utils/mediaSecurity.js, stream URLs are protected with HMAC-SHA256 signatures:

const expectedBuffer = Buffer.from(expectedSignature, "hex");
const receivedBuffer = Buffer.from(signature, "hex");

// Prevents side-channel timing attacks!
const matches = crypto.timingSafeEqual(expectedBuffer, receivedBuffer);

Why timingSafeEqual matters: Standard string equality (===) terminates at the first mismatched byte, leaking cryptographic hints to attackers measuring latency. timingSafeEqual always executes in constant time.

Database Engineering: Schemas, Indexes & Pipelines

📊 Multi-Stage Aggregation Pipeline: Channel Profile

In src/controllers/user.controller.js (getUserChannelProfile), a single aggregation computes subscriber counts, subscriptions, and whether the current viewer is subscribed: 

const channel = await User.aggregate([
    { $match: { username: username.toLowerCase() } },
    {
        $lookup: {
            from: "subscriptions",
            localField: "_id",
            foreignField: "channel",
            as: "subscribers"
        }
    },
    {
        $lookup: {
            from: "subscriptions",
            localField: "_id",
            foreignField: "subscriber",
            as: "subscribedTo"
        }
    },
    {
        $addFields: {
            subscribersCount: { $size: "$subscribers" },
            channelsSubscribedToCount: { $size: "$subscribedTo" },
            isSubscribed: {
                $cond: {
                    if: { $in: [req.user?._id, "$subscribers.subscriber"] },
                    then: true,
                    else: false
                }
            }
        }
    }
]);
⚡ Indexing Strategy
  • User: username and email indexed with unique constraints for O(1) login lookups.
  • Video: title text-indexed for fuzzy search queries; owner indexed for fast channel queries.
  • Subscription: Compound index on { subscriber: 1, channel: 1 } prevents duplicate subscriptions.
📑 Pagination with AggregatePaginate

All high-volume listing endpoints (getAllVideos, getVideoComments, getUserTweets) use mongoose-aggregate-paginate-v2. This prevents database memory exhaustion by slicing cursor results at the database tier using $skip and $limit stages.

🔄 Centralized Error & Async Handling Pattern

PulseCast eliminates repetitive try-catch boilerplate using higher-order functions: 

// src/utils/asyncHandler.js
const asyncHandler = (requestHandler) => {
    return (req, res, next) => {
        Promise.resolve(requestHandler(req, res, next)).catch((err) => next(err));
    };
};

// src/utils/ApiError.js
class ApiError extends Error {
    constructor(statusCode, message = "Something went wrong", errors = []) {
        super(message);
        this.statusCode = statusCode;
        this.errors = errors;
        this.success = false;
    }
}
🌊 Streams & Backpressure Management

When streaming 206 chunk slices, Node.js read streams automatically handle backpressure:

  • If a client is on a 3G mobile network, the TCP socket buffer fills up.
  • stream.pipe(res) detects the TCP buffer is saturated and pauses fs.createReadStream.
  • When the client consumes data and the buffer drains, the stream automatically resumes reading from disk, preventing server RAM from filling up.

The Comprehensive Interview Question Bank

50+ senior-level backend and systems interview questions categorized by topic, complete with technical answers, simple analogies, and code references.

Q1: How does HTTP 206 Partial Content work under the hood? [Streaming] Hard

Simple Analogy: Instead of ordering a whole book shipped to you at once, you ask the publisher to photocopy pages 50 through 100 on demand.

Technical Explanation: The client sends an HTTP header: Range: bytes=0-1048575. The server validates that the range falls within file bounds (returning 416 Range Not Satisfiable if not). It calculates the chunk length, sets Content-Range: bytes 0-1048575/total_size, and uses Node.js fs.createReadStream(path, { start, end }) to pipe that exact slice into the HTTP response stream with status code 206 Partial Content.

PulseCast Reference: Implemented in src/controllers/stream.controller.js lines 50-98.

Follow-Up Question: "What happens if a browser requests multiple ranges at once?" — The server responds with Content-Type: multipart/byteranges; boundary=... separating slices with MIME boundaries.

Q2: Why is the TUS protocol superior to chunked multipart uploads? [Ingestion] Medium

Simple Analogy: Standard upload is mailing a single 500-page manuscript; if one page gets lost in the mail, you have to resend all 500 pages. TUS is like sending page-by-page with receipt tracking so you only resend from the last confirmed page.

Technical Explanation: Standard multipart forms have no native state reconciliation. TUS creates an upload resource (POST), pushes sequential byte chunks with known offsets (PATCH), and allows the client to query the exact byte offset (HEAD) after connection drops to resume without duplicating transferred data.

PulseCast Reference: Handled by @tus/server in src/services/tus.service.js.

Q3: How do you prevent playback synchronization drift in a Watch Party? [WebSockets] Hard

Technical Explanation: Because client clocks and network latencies fluctuate, peers inevitably drift out of sync. Rather than hard seeking on every minor offset (which causes audio stutter), PulseCast uses a 3-tier drift compensation algorithm: 1. Under 150ms: Deadband (no adjustment, transparent). 2. 150ms to 1.5s: Adjusts video.playbackRate = 1.05 or 0.95 to subtly speed up or slow down until convergence. 3. Over 1.5s: Hard seek (video.currentTime = serverTime).

PulseCast Reference: frontend/src/components/WatchPartyRoom.jsx lines 67-82.

Q4: Why use crypto.timingSafeEqual for signed stream URLs? [Security] Hard

Technical Explanation: Standard JavaScript string comparison (===) uses short-circuit evaluation, returning false as soon as the first mismatched byte is encountered. Attackers can measure response time variations (sub-microsecond timing attacks) to brute-force valid signatures character by character. crypto.timingSafeEqual compares byte buffers in constant time, leaking zero timing telemetry.

PulseCast Reference: src/utils/mediaSecurity.js lines 42-49.

Answer

Between 150ms and 1.5s, it adjusts playbackRate to 1.05x or 0.95x for smooth convergence without audio pitch distortion.
